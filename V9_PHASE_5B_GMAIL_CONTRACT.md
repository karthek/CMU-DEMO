## 1. Gmail synchronization model and identity

**Google:** Message `id` is immutable. `threadId` identifies its conversation.
`historyId` identifies the last history record modifying the message. `internalDate`
is epoch milliseconds used for inbox ordering: normally Google SMTP acceptance
time, but imported mail may use the sender's Date header instead. Labels are
mutable metadata. The resource exposes no separate immutable content revision.
Its parsed payload consists of MIME parts and headers. [G1]

The sync guide recommends initially caching FULL/RAW content and subsequently
retrieving MINIMAL because labels may change. It recommends a recent message's
history checkpoint for partial sync. [G2] Draft replacement destroys/replaces its
underlying message and changes message ID, unlike the stable draft container. [G12]

**Decision:** The concepts remain distinct:

| Concept | Core mapping / meaning |
|---|---|
| Message.id | `message_id`, scoped by provider and configured stable account ID. Never use RFC Message-ID header as this key. |
| Thread ID | Conversation evidence, not booking/segment identity. For the initial Gmail normalization profile, set optional `thread_id=None`; conversation grouping is not needed by extraction. |
| Message.historyId | Mailbox change evidence, never immutable content version or airline sequence. |
| internalDate | `received_at`, aware UTC derived exactly from integer milliseconds. Source basis is explicit; it is not proof of sender time, flight date or content freshness. |
| Retrieval timestamp | Runtime attempt time, distinct from evidence time. Existing core `as_of` records processing/checkpoint time; do not claim it is an exact per-message fetch timestamp. |
| Completion cursor | Opaque scoped envelope containing a validated mailbox history checkpoint; not a message version or timestamp. |
| `version` | Versioned canonical evidence fingerprint described in section 2. |

Use configured immutable account identity bound to the authorized mailbox; neither
`me` nor recipient text is an account/traveler identity authority. Account renames,
rebinds or mailbox replacement require runtime review rather than silently reusing
an account key. Label changes (including read/unread, archive, trash) can change
history without changing content. Google does not provide an exhaustive promise
about every future resource field; the adapter must fingerprint every successful
normalized reread rather than assume metadata and payload are forever identical.
No unseen past body revisions can be reconstructed from ID-only history records.

## 2. Frozen immutable-evidence version strategy

**Decision: `mail-evidence/v1:sha256:<lowercase hex>`**, generated by the new pure
`mail_evidence_version(MailMessage)` helper after normalization. This is an opt-in
contract for a new source, not a rekeying/migration of previously stored versions.

Hash the UTF-8 bytes of a JSON object with sorted keys, separators `(',', ':')`,
`ensure_ascii=True`, and `allow_nan=False`. The exact field set is provider,
account_id, message_id, sender, subject, text_body, html_body, received_at (UTC
ISO string), thread_id, recipients (ordered JSON array), and provenance containing
source, observed_at (UTC ISO string), retrieved_by. The input `version` is excluded.
No labels, history record IDs, cursor, fetch time, snippet, size estimate, MIME
boundary, part IDs or transport encoding occur in this normalized schema.

The adapter constructs a local provisional MailMessage, computes the helper result,
then uses dataclass replacement to set `version`; a provisional value must never
be emitted or persisted. The helper performs no I/O and mutates nothing.

Frozen Gmail normalization profile:

- `provider=GMAIL`; account/message identity as above; `thread_id=None`.
- `received_at=internalDate` in aware UTC. Provenance source is the fixed string
  `gmail-api/internal-date/mail-normalization-v1`, observed_at equals received_at,
  retrieved_by is PROVIDER. This is receipt-based mail evidence provenance, not
  a claim that the body was observed operationally at that time. Never feed this
  timestamp into operational-flight freshness or use it to prove airline authority.
- Sender/subject/text use existing MailMessage normalization. Recipients are the
  sorted unique normalized addresses from To and Cc; no inferred Bcc/envelope
  recipient or configured traveler substitution. Empty recipients are allowed.
- HTML retains decoded evidence with CRLF/CR normalized to LF only; no whitespace
  collapsing, DOM reserialization or Unicode normalization beyond decoding.
- No sent_at field is required now: Date is not used for extraction/order and no
  suitable content-modification instant is documented. Exact fetch audit and
  additional authenticated-header evidence need later versioned contracts if needed.

Why fingerprint instead of Message.id alone: our normalized evidence also includes
selected header/body representation and provenance; conflicting rereads must be
representable and auditable even though Gmail supplies no content revision token.
Why not historyId: label-only activity would create artificial itinerary versions.
Why not retrieval time/cursor: rereads would never be idempotent. Why not raw MIME
bytes: boundary/encoding changes need not change the evidence extraction consumes.
Why not extracted itinerary fields: that would discard conflicting input evidence
and make message identity dependent on airline parser behavior.

Tradeoffs: HTML formatting differences can create distinct evidence versions even
when their extraction results agree; core event deduplication keeps equivalent
booking facts together. SHA-256 is a collision-resistant identifier, not proof of
authenticity. Repository equality checks still reject different bytes under the
same key. There is no ordering between fingerprints: conflicting schedules cannot
supersede one another without deterministic travel-document authority.

Hashing covers every currently serialized evidence field except version, including
stable provenance, so legitimate changes cannot reuse an immutable key accidentally.
Changed normalization/profile rules require explicit review, a new version namespace
and a reprocessing strategy. Never silently change v1, add serialized defaults to
old records, or recompute old stored versions. Existing canonical booking/segment/
event identities do not depend on this fingerprint and remain unchanged.

## 3. Full synchronization mapping

**Google:** `messages.list` supports `q`, label filtering, inclusion of spam/trash,
pageToken and nextPageToken; page size defaults to 100 and is capped at 500.
Returned entries contain id/threadId only; resultSizeEstimate is an estimate, not
completion evidence. [G3] `messages.get` retrieves an identified Message using a
selected format. [G4] FULL supplies parsed payload, RAW supplies encoded message
bytes; METADATA/MINIMAL omit content needed here. [G5] Date searches support epoch
seconds; calendar-date strings use PST, and API search differs from UI alias and
thread-wide searching. [G6]

**Decision:** Use FULL for body normalization; never extract from list entries or
snippets. Initial scope is all non-draft mailbox messages, including spam/trash,
within the explicit 365-day lower bound. No sender, airline, INBOX or travel-keyword
query is allowed in this profile: such filters could suppress booking changes.
Spam/trash inclusion is discovery coverage, not trust approval.

Query with an epoch-second lower bound rounded down with one extra second of
overlap, then enforce `received_at >= since` locally at millisecond precision.
Exclude DRAFT explicitly from evidence. Freeze lookback/profile in cursor scope;
changing discovery scope requires full resync. Do not silently exclude archived or
trashed confirmations. Do not use the moving `newer_than:365d` expression.

Empty/missing messages arrays are treated as empty only in a structurally valid
successful list response. Follow nextPageToken even on an empty page. No next token
ends that enumeration; never stop at resultSizeEstimate. Missing bodies, invalid
page shapes or token cycles are failures, not empty mailboxes. Disappearance between
list and get has no documented transaction/snapshot guarantee: a message-get 404
fails this full attempt as NOT_FOUND; never silently skip it and advance checkpoint.

### Conservative bootstrap/checkpoint policy (design inference)

Profile `historyId` describes the mailbox's current history record, and is readable
with the selected scope. [G8] Unlike choosing a message, this works conceptually for
an empty result set. The history method's accepted-source wording does not explicitly
name getProfile; this is an inference from the shared mailbox-history definition,
not an additional guarantee. Validate it with a successful history read, never assume.

For the first bounded adapter, require a quiet full-scan window:

1. Read profile checkpoint H0 before enumeration. Keep it only in attempt memory.
2. Complete every list page/get/body-normalization step under fixed scope/bounds.
3. Validate H0 by exhausting history.list from H0 without label/type filters.
   Require no changes and terminal historyId equal to H0. Recheck profile after
   body fetches; require the same H0. Any change or inconsistent checkpoint fails
   this attempt as retryable UNAVAILABLE; do not emit a completed full batch.
4. Emit normalized pages with a completion cursor containing that validated H0
   only on the final page. A genuinely empty successful batch still has this cursor.
5. Core atomically commits evidence/projection/visibility/cursor and clears recovery.

This is intentionally stricter than Google's general sync recipe. It avoids selecting
a post-scan checkpoint that skips messages arriving during pagination. New changes
after the final check remain after H0 for the next incremental run. Busy mailboxes
may not complete within bounds; fail visibly, never loop indefinitely. If an empty
mailbox has no usable history checkpoint or validation returns 404, full recovery
does not succeed and no synthetic cursor is created. Improving availability with
a scan-plus-catch-up algorithm is a separately reviewed optimization.

Google does not promise a transactional list snapshot or formal cross-endpoint
consistency model in these references. Quiet-window validation reduces detectable
races; it is not a claim of distributed snapshot isolation. Unknown/inconsistent
coverage cannot support reliable activation. Real-mail activation remains absent.

## 4. Incremental synchronization and completion cursor

**Google:** history.list returns records after startHistoryId, in increasing history
order; IDs have gaps. Specific change arrays are messagesAdded, messagesDeleted,
labelsAdded and labelsRemoved; generic messages may duplicate their entries.
Messages usually contain only id/threadId. Response historyId is current mailbox
history; after pagination ends it can be retained for the next request. [G7]

**Decision:** Parse a versioned opaque cursor envelope privately in the future
adapter: `{format, account binding, discovery profile, initial lower bound,
checkpoint}`. Core stores the string without interpreting Gmail names/numbers.
Checkpoint equals terminal successful history.list response historyId, never the
largest message historyId, last event seen, pageToken, timestamp or incremented ID.
Reject invalid/mismatched scope envelopes as CURSOR_EXPIRED to require full recovery.

Fetch all history pages using the same start checkpoint. No label/history-type
filters. Ignore generic messages when processing typed changes; deduplicate IDs
and identical typed events. Treat ordering as mailbox visibility order only. No
exactly-once delivery, cross-page snapshot or intra-record ordering guarantee is
assumed. Detect token cycles, malformed/decreasing checkpoints and conflicting
same-record evidence; fail conservatively.

Buffer the complete bounded vendor batch before producing core-visible pages.
For every affected non-deleted message, get FULL and normalize current evidence.
Coalesce repeated sightings of one ID into one final normalized message. For proven
terminal permanent deletion, emit only its removal identity; never also emit its
earlier addition in the same batch. Contradictory or unverifiable terminal state
fails INVALID_RESPONSE rather than ordering events by receipt time. A get 404
without covered permanent-deletion evidence fails NOT_FOUND and preserves cursor.

Require post-fetch profile checkpoint to equal the history terminal checkpoint;
otherwise fail retryable UNAVAILABLE and restart from the persisted cursor. This
bounded consistency check avoids committing a fetched state newer than the claimed
checkpoint. Identical rereads keep fingerprints; label activity cannot change them.
Terminal success with no relevant messages still emits an empty normalized delta
and the terminal cursor. Never interpret it as full-mailbox absence.

Initial lower bound in the cursor remains fixed for incremental coverage. `since`
is used for full enumeration; the service's later rolling since does not narrow an
existing delta stream. Only newly discovered messages below the initial lower bound
are outside discovery scope; removals always retain their source IDs. Scope/profile
changes require explicit full sync. No claim of retaining the entire mailbox.

Vendor pages need not correspond one-for-one to MailSyncPage. The adapter may return
bounded in-memory normalized pages after coalescing; its continuation token must
bind to the attempt, account and scope. No durable partial checkpoint, implicit
resume after lost attempt state, or provider I/O inside the SQLite transaction.
Phase 5C must separately bound vendor history pages, requests, MIME bytes and elapsed
attempt time, in addition to existing core 100-page/10,000-item normalized bounds.

## 5. Cursor expiration and recovery

**Google:** Invalid/out-of-range startHistoryId typically produces HTTP 404 and calls
for full synchronization. Availability is often a week or longer, but can be only
hours; no fixed minimum retention should be assumed. [G2], [G7]

**Decision:** A validated history request returning 404 maps to CURSOR_EXPIRED,
not message NOT_FOUND. Persistent FULL_RESYNC_REQUIRED survives timeout, auth,
unavailable and all other failures. Incremental completion cannot clear it; only a
qualifying complete full transaction can. If bootstrap validation itself expires,
fail the full attempt and retain the requirement. No silent fallback, empty snapshot,
or invented checkpoint. Generic 400 does not automatically mean expired history;
an explicitly diagnosed malformed local cursor is a recovery requirement, whereas
an unexplained bad request remains a nonretryable invalid-response/request failure.

## 6. MIME and body normalization boundary

**Google:** MessagePart has MIME type, headers, filename, body and nested parts;
top-level headers include From/To/Subject. Containers can have empty bodies. [G1]
MessagePartBody.data is base64url; when attachmentId exists, body bytes require a
separate attachment retrieval. Size describes decoded part bytes. [G9]

**Decision:** Future adapter handles transport/MIME only; extractor receives existing
MailMessage strings, not Gmail payload dictionaries. Freeze this bounded initial
normalization profile:

- Read header names case-insensitively; unfold valid continuations and decode encoded
  header words strictly. Require one unambiguous From mailbox and Subject value;
  conflicting duplicates or invalid addresses fail INVALID_RESPONSE. Missing subject
  maps to empty string; no sender can be guessed. Parse To/Cc as described above.
- Walk multipart structure in document order. Accept at most one non-attachment
  text/plain and one non-attachment text/html body leaf. Both alternatives are kept,
  so deterministic extraction can detect contradictory facts. Multiple distinct
  same-type leaves, nested message/rfc822, encrypted content or unsupported body
  structure fail UNSUPPORTED_CAPABILITY rather than selecting a convenient part.
- Strict base64url decoding; strict declared charset decoding with a fixed bounded
  codec allowlist (UTF-8, US-ASCII, ISO-8859-1, Windows-1252). Missing charset is
  accepted only for ASCII bytes. Unsupported charset fails UNSUPPORTED_CAPABILITY;
  malformed bytes fail INVALID_RESPONSE. No replacement characters or guessed
  UTF-8 fallback. Do not apply MIME transfer decoding twice to API-decoded body data.
- FULL payload transfer-decoding details beyond base64url are not exhaustively
  specified by Google here. For this initial bounded profile, accept absent,
  7bit, 8bit or binary Content-Transfer-Encoding only; other declared encodings
  fail UNSUPPORTED_CAPABILITY. Do not guess quoted-printable/base64 transfer handling
  or double-decode. Widening this profile needs documented/fixture-backed resolution.
- If a selected text leaf uses attachmentId, retrieve its bytes through the future
  read boundary or fail; empty data is not proof of empty content. Do not pass
  incomplete text as a successful message. Non-body attachments are excluded from
  this body-only profile; attachment-only messages are unsupported. No PDFs/OCR,
  calendar attachments, airline parsing or remote HTML image/script retrieval.
- Preserve HTML evidence as specified in section 2. Existing core HTML-to-text logic
  excludes scripts/styles. No mutation of Phase 3 extraction normalization.

Unsupported messages currently fail the bounded sync rather than being mislabeled
NOT_TRAVEL. This can block progress; a durable per-message quarantine/completion
contract is deferred and must not be invented inside the adapter. Any future wider
MIME profile needs explicit review and replay/version compatibility tests.

## 7. Tombstones and mailbox visibility

**Google:** messagesDeleted means deletion, specifically not trash. [G7] TRASH,
SPAM, INBOX and UNREAD are system labels; label membership is per message, and a
thread label is not proof that every message shares it. [G10]

**Decision:** Permanent deletion maps to removed_message_ids scoped by provider/
account. Trash, archive, ordinary label removal and label additions do not remove
mailbox visibility under the inclusive profile. They may trigger rereads but are
not content fields. Drafts remain excluded; their replacement is not flight change.
Full absence updates visibility only within successful declared lookback coverage.
Historical messages/events/provenance/revisions remain immutable.

MAIL REMOVAL != FLIGHT CANCELLATION. No removal, get 404, empty delta, label or cursor
event cancels a canonical segment. Only deterministic document evidence can assert
booking cancellation; operational flight status comes from a later flight provider.

## 8. OAuth and permissions

**Decision:** Select only `https://www.googleapis.com/auth/gmail.readonly` for future
background discovery/history/content reads. The relevant list/get/history/profile
methods permit it. [G3], [G4], [G7], [G8]. Google's scope list identifies readonly as
restricted; metadata excludes bodies, and add-on current-message scopes are scoped
to add-on use. [G11] Metadata is also insufficient for FULL/RAW. [G5]

No modify, compose, send, labels-write, or full mail.google.com grant. A query is
not an OAuth restriction to travel mail: readonly can expose broader mailbox data.
Consent/account/domain policy and applicable restricted-scope verification remain
runtime deployment gates, not completed by this research. No OAuth implementation,
permission request or token storage was performed. Credentials belong in runtime
configuration/secret storage, never ordinary mail evidence tables or logs. Calendar
read and future write permissions remain independent.

## 9. Error translation

Google distinguishes HTTP statuses and structured error reasons: 401 authentication,
403 permissions or quota, 429 rate limits, 400 bad requests, and 500/502/503/504
server failures. Its guide recommends backoff for transient limits/errors. [G13]
The following mapping is our normalized policy, not vendor error leakage:

| Gmail/transport condition | ProviderErrorCode | Retryability / decision |
|---|---|---|
| 401 authError | AUTH_REQUIRED | false; runtime reauthorization/refresh boundary, no OAuth here |
| 403 permission/domainPolicy/scope denial | PERMISSION_DENIED | false; never widen scopes automatically |
| 403 rateLimitExceeded/userRateLimitExceeded or 429 | RATE_LIMITED | true with bounded backoff and safe delay if available |
| 403 dailyLimitExceeded | RATE_LIMITED | false for immediate retry; runtime/operator quota decision |
| 500/502/503/504 | UNAVAILABLE | true, bounded retry |
| Transport timeout | TIMEOUT | true, bounded retry; no cursor commit |
| Transient connection/DNS interruption | UNAVAILABLE | true; configuration/TLS validation failures are not blindly retryable |
| Message/attachment get 404 | NOT_FOUND | false for identical request; fail batch unless covered deletion establishes final removal |
| History read 404 for valid request scope | CURSOR_EXPIRED | false for incremental retry; persistent full recovery required |
| Malformed JSON/payload, inconsistent ID/page, unexplained 400 | INVALID_RESPONSE | false; fix mapping/request rather than fabricate evidence |
| Unsupported MIME/body capability | UNSUPPORTED_CAPABILITY | false; no incomplete evidence success |

Only three enum members are added now: TIMEOUT, NOT_FOUND, UNSUPPORTED_CAPABILITY.
AMBIGUOUS_IDENTITY remains deferred for future flight association; ambiguous mail
normalization is INVALID_RESPONSE. Core stale-data status remains separate. Safe
envelopes contain category/retryability/delay only, never raw reason text, URLs with
tokens, credentials or message bodies. Unclassified adapter exceptions must still
fail closed through existing synchronization handling.

## 10. Provider-neutral contract mapping and compatibility

| Boundary | Frozen contract |
|---|---|
| MailSource request | Existing since/cursor/page_token; source bound to provider/account; null cursor full, non-null incremental; opaque adapter token scopes as above |
| MailMessage | Existing dataclass unchanged; immutable scope/content/receipt/provenance; optional HTML, optional thread, recipient tuple; no Gmail fields added |
| Version helper | New opt-in pure fingerprint, all evidence fields except version; old IDs/serializers untouched |
| MailSyncPage | Existing immutable message/removal tuples and exactly one continuation/completion at application boundary; no constructor change needed |
| Failure | Existing ProviderResult/ProviderError envelope plus three enum values |
| Persistence | BookingRepository is migration-2 entry point; complete batch commit only, unchanged checkpoint/rollback/resync invariants |
| Authority | Adapter supplies normalized mail evidence and source visibility; core owns exact booking identity, document authority, reconciliation and readiness |

No need to add sent/provider-update/fetch fields to immutable MailMessage for this
profile. Their addition would alter replay bytes without improving current extraction.
Per-fetch audit can be designed later outside immutable evidence. Labels and thread
grouping are not required core fields for itinerary discovery. No changes to migration
SQL/checksums, canonical/event hashing, old evidence, extraction, V8 code or tests.

## 11. Remaining unknowns and exact Phase 5C gate

All nine requested semantic boundaries have explicit decisions, but this is a
**bounded fail-closed contract**, not verified live mailbox behavior. Official docs
do not establish transactional snapshots, exhaustive same-ID field mutability,
intra-record ordering, missing-ID race outcomes, every MIME decoding detail, or
usable history for every empty/new mailbox. Profile checkpoint use is a documented
design inference validated by a history request. None permits guessing or cursor
advancement on failure. Busy/unsupported mailboxes may remain blocked.

Safe to freeze for a separately authorized, offline-tested Phase 5C Gmail read
adapter **under these restrictions**. This document does not authorize Phase 5C.
Before approval, review the inclusive spam/trash discovery scope, quiet-window
availability tradeoff and unsupported-MIME whole-batch failure policy. Phase 5C
must demonstrate stubbed tests for: bootstrap and empty results; multi-page history;
mid-scan mutation; repeated/label-only changes; deletion races; scope/cursor mismatch;
body decoding/limits; timeout/auth/rate limits; expiration and failed recovery;
cross-restart evidence replay; and no partial cursor commit. No live OAuth/account
use is implied. Unsupported cases stay failures until separately reviewed.

Sustained ingestion still requires bounded/scalable all-history reprojection;
another migration still requires consolidated runner ownership. Real templates,
authenticated mail trust, operational planning, MCP/workers and calendar HITL remain
later scopes. Sender matching is not authenticated origin. No real mail activates
V8 merely because a Gmail read succeeds.
